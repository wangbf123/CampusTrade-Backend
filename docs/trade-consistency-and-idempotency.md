# 预约交易一致性与请求结果幂等

## 技术选择

MySQL 决定商品和订单状态，Redis 不承担交易正确性的唯一判断。
确认通过 `ON_SALE -> RESERVED` 的条件更新绑定 `reserved_order_id`，只有该订单可以释放或售出商品。
确认、取消已确认订单、完成交易均以“商品 -> 订单”的顺序修改，订单、商品和通知 Outbox 位于同一个数据库事务。
任一条件更新失败会抛出业务冲突并回滚整笔数据库事务。

确认 SQL 限制 `PENDING AND expire_at > CURRENT_TIMESTAMP(6)`；超时 SQL 限制
`PENDING AND expire_at <= CURRENT_TIMESTAMP(6)`，工作线程提前触发不会关闭未到期订单。
订单期限和数据库连接会话统一使用 UTC；API 的不带时区时间字段按 UTC 解释。
商品已被预约时不能直接下架，应先取消关联订单。下架使用条件更新，避免旧快照覆盖新的占用状态。

## 显式请求键

创建预约支持原有 `X-Idempotency-Key` 请求头。
规范化后的键在用户范围内唯一、区分大小写，最长 128 个字符；商品、预约时间、备注参与 SHA-256 请求摘要。

`appointment_idempotency` 的主键为 `(user_id, request_key)`。
MySQL 唯一键竞争和 `SELECT ... FOR UPDATE` 使并发相同请求等待首次事务完成。
成功后在同一事务保存订单 ID 与完整的初始 `OrderResponse` JSON；重试返回相同快照，不重复创建订单或通知。
即使订单已确认或原预约时间已过，原成功请求仍可重放。不同载荷使用相同键返回 409。
新预约仍要求未来时间；该校验在重放判断之后执行。
业务操作失败时请求键、订单、Outbox 随事务一起回滚，同键可以重试。

成功键没有自动 TTL，不会在短 TTL 结束后重复执行。未来若增加清理，需要明确保留期限及键重复使用协议。
缺少请求键的调用保持现有指纹 TTL 防重复行为：重复返回 409，而非结果重放。
HTTP 层的鉴权、参数格式校验和限流仍然生效。

## 内存开发模式

内存仓库使用带 owner 校验的原子商品更新、带期限校验的订单更新，订单服务串行化跨记录操作。
显式键的成功响应保存在内存；重启后会丢失，不能用于宣称持久幂等或数据库事务回滚保证。
生产部署应使用 `mysql` profile。

## 数据迁移

Flyway V5 增加占用订单与请求结果表。
对于旧的 RESERVED 商品，只有恰好一个 CONFIRMED 订单时自动绑定。
有零个或多个已确认订单的旧记录保留空 owner，后续释放/售出会被拒绝，需要核对历史数据后处理。
迁移不会通过任意选择订单掩盖不一致。

本次 profile 从原 `serverTimezone=Asia/Shanghai` 明确为 UTC，V5 不会自动转换旧 DATETIME。
该 JDBC 参数本身不能证明历史 DATETIME 的实际语义：上线前应结合原 JVM/数据库会话时区、部署配置和已知订单事件时间核对。
若历史值按 Asia/Shanghai 本地时间存储，需要先在备份与测试副本中验证转换方案，再通过独立的数据迁移统一为 UTC。
不要在原业务库盲目加减 8 小时；存在历史数据且语义未核对时，应先保持原部署时间配置，不直接上线此 UTC 切换。
本次自动化验证只使用新建隔离库，未转换现有业务数据。

当前响应仍使用无偏移的 ISO LocalDateTime，接口时间契约是 UTC；客户端显示时应显式按 UTC 解析再转换用户时区，
不能依赖浏览器把无偏移字符串当成本地时间。若客户端已有不同时间约定，应同时升级适配后发布。

## 验证与表述边界

单元测试覆盖占用竞争、错误 owner、期限条件、订单服务并发与请求重放。
`MysqlOrderConcurrencyTest` 在真实 MySQL 上使用生产仓库、Flyway 与事务管理器，创建随机独立数据库并在结束后删除。
启用方式为 `CAMPUS_MYSQL_IT=true`，通过环境安全提供 `CAMPUS_MYSQL_IT_PASSWORD`，
可设置 `CAMPUS_MYSQL_IT_ADMIN_URL` 和 `CAMPUS_MYSQL_IT_USER`；运行 `mvn test`。
测试账号需要创建和删除临时数据库权限，不应使用实际业务库运行验证。

真实库实验验证 24 个订单竞争同一商品只确认一个、完成/取消竞争的状态一致、到期确认回滚商品占用、
重复超时只转换一次、24 个同键请求只创建一份订单与 Outbox，以及故障后的整笔回滚和重试。
这些是正确性实验，不代表生产吞吐容量或延迟表现。

可据实描述为：通过 MySQL 条件更新、订单占用归属和本地事务保障交易状态一致，
实现数据库持久化请求结果幂等，并使用真实数据库并发与回滚实验验证竞态处理。
